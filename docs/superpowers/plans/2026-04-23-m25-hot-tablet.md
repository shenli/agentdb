# M25: hot-tablet detection + bulk load-shed

Status: in progress (2026-04-23).

The prototype has everything needed to *move* load between
tablets: `set_shard` reassigns individual shards, the reaper
reassigns orphaned ones, LocationProxy refreshes push new
routing decisions to live boxes, cross-node forwarding
delivers writes regardless of which node owns the target.
What's missing is the signal — **which tablet is hot, and
when?** — and a convenient bulk operation to act on that
signal.

## What's in / out

**In:**
- **Sliding-window rate tracker on `BoxMetrics`.** 60-second
  window bucketed into 6 × 10s slots. Records `appends` and
  `admission_waits` per slot. On demand, computes
  `appends_per_sec` and `admission_wait_ratio =
  waits_in_window / appends_in_window`. Zero heap allocation
  on the hot path; writes are atomic adds into the current
  slot.
- **`HotTabletDetector`.** Background task on the scheduler
  leader. Samples every `AGENTDB_HOT_DETECT_TICK_SECS`
  (default 10s). A tablet flips to "hot" when its
  `admission_wait_ratio > AGENTDB_HOT_WAIT_RATIO` (default
  0.3 — 30% of writes had to wait for a permit) across
  `AGENTDB_HOT_CONSECUTIVE` consecutive samples (default 3 —
  ~30 seconds of sustained saturation). A tablet flips back
  to "cool" after one sample below threshold. The detector
  keeps its output in memory only; no meta-store
  persistence (transient signals don't deserve SQLite
  writes).
- **Admin endpoints:**
  - `GET /api/admin/tablets/hot` — list currently-flagged
    tablets with `{tablet_id, appends_per_sec,
    admission_wait_ratio, flagged_at_ms}`
  - `POST /api/admin/tablets/:id/shed` — move
    `fraction` (default 0.5) of this tablet's currently-
    assigned shards to a destination tablet. Body:
    `{ "to_tablet_id": i64 | null, "fraction": f64 | null }`.
    If `to_tablet_id` is null, pick the least-loaded live
    tablet from the detector's snapshot.
- **CLI:**
  - `agentdb show-hot-tablets`
  - `agentdb shed-tablet <id> [--to N] [--fraction F]`
- **Prometheus exposition** for the new rate gauges:
  `agentdb_appends_per_sec` and
  `agentdb_admission_wait_ratio` (per box, same attribution
  as the existing counters).

**Out of scope (explicit):**
- **Dynamic tablet/box creation.** A real split creates a
  *new* tablet with id ≥ num_boxes, which the prototype's
  fixed `BoxRegistry.boxes: Vec<Arc<Box_>>` doesn't
  support. "Split" in this PR means "redistribute existing
  shards across existing tablets." Shipping dynamic tablet
  creation requires growing the box array at runtime (and
  a new lease-acquisition path), which is a separate PR.
- **Automatic shed.** The detector flags tablets; an
  operator (or, eventually, a scheduler policy) calls
  `shed`. Automatic shed would need calibrated thresholds,
  hysteresis, and a way to avoid thrash — premature without
  production data.
- **Hot-key detection.** "One session is hot, not the whole
  tablet." Requires per-session metrics, which the
  prototype doesn't track. Future work.
- **Latency percentiles (p99 etc.).** The admission-wait
  ratio is a cheap proxy. Histograms would be nicer but
  need a third-party histogram crate; the ratio signal is
  actionable on its own.

## Design

### Rate tracker

```rust
pub struct RateWindow {
    // 6 × 10s slots; the "current" slot rotates every 10s.
    slots: [Slot; 6],
    current: AtomicUsize,   // index into slots
    last_roll_ms: AtomicI64, // wall-clock of the last roll
}
struct Slot {
    appends: AtomicU64,
    waits: AtomicU64,
}
```

Hot path: `record_append()` and `record_admission_wait()`
call `maybe_roll()`, which checks if `now_ms -
last_roll_ms >= 10_000` and, if so, atomically advances
`current` and zeroes the new slot. Zero contention: a
single `compare_exchange` per 10s roll, sharing the cost
across all writers in the window.

Read: `window_snapshot()` sums appends+waits across all
slots and divides by elapsed seconds. Exact enough for
hot-detection; not claimed to be transactional.

### Detector

Simple state machine per tablet:
```
cool --(ratio > threshold for N consecutive)--> hot
hot  --(ratio <= threshold once)------------> cool
```

`AGENTDB_HOT_CONSECUTIVE` is the hysteresis knob. Spikes
(one tick over threshold) don't flip the state.

### Shed endpoint

```
POST /api/admin/tablets/{id}/shed
Body: { "to_tablet_id": i64 | null, "fraction": f64 | null }

1. Resolve source tablet (id exists in tablets table).
2. Resolve destination:
   - If body.to_tablet_id is Some, use it.
   - Else pick the tablet with lowest appends_per_sec from
     the detector snapshot (excluding the source).
   - Error 400 if no viable destination.
3. Fetch shards currently overridden to source via
   meta_shards::list_by_tablet. Compute N = (count ×
   fraction).ceil() (clamp to count).
4. Update N of those shards' `tablet_id` to destination
   via meta_shards::set_assignment (batched).
5. Call LocationProxy::refresh() locally so the write path
   sees the new routing on the next request.
6. Return 200 with { "moved_shards": [...], "count": N,
   "to_tablet_id": <dest> }.
```

No data migration — the old events stay on the source
tablet. Same limitation as `set_shard`; same rationale.

### Admin shape

Mirrors the existing `/api/admin/shards` and
`/api/admin/tablets` endpoints. Returns JSON; OpenAPI
snapshot updates.

## Test plan

Unit tests (agentdb-core):
- Rate tracker rolls slots correctly across time
- appends_per_sec math on a known sequence
- Detector flips cool→hot after N consecutive, flips back
  on one cool sample

Integration (agentdb-api):
- Saturate one tablet via burst writes to a single session
  overridden to it
- Poll `/api/admin/tablets/hot` until it's flagged
- POST `/api/admin/tablets/:id/shed { fraction: 0.5 }`
- Assert the shed response reports the moved shards
- Verify subsequent writes split across the two tablets
- Verify `/api/admin/tablets/hot` eventually empties when
  pressure stops

## Rollout

Zero config change; detector starts on the scheduler leader
automatically. Off by default in the sense that nothing acts
on the signal until an operator calls `shed`. Env-var
thresholds are tunable.

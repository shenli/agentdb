# Deploying AgentDB on S3

AgentDB's default backend is RocksDB on local disk — fine for dev and
for single-node deployments. This guide covers the opt-in "SlateDB on
S3" shape, which moves both the operational KV and the cold-segment
store onto object storage.

## Env vars

| var | default | purpose |
|---|---|---|
| `AGENTDB_KV_BACKEND` | `rocksdb` | `rocksdb` or `slatedb` |
| `AGENTDB_OBJECT_STORE` | `local` | `local` or `s3` |
| `AGENTDB_SLATEDB_PATH` | `agentdb/slate` | Key prefix for SlateDB's LSM state |
| `AGENTDB_S3_BUCKET` | — | Required when `AGENTDB_OBJECT_STORE=s3` |
| `AGENTDB_S3_REGION` | `us-east-1` | AWS region |
| `AGENTDB_S3_ENDPOINT` | (AWS) | Custom endpoint for MinIO, R2, etc. |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | (AWS env chain) | Credentials |

Setting `AGENTDB_KV_BACKEND=slatedb` with `AGENTDB_OBJECT_STORE` unset
is legal (SlateDB runs against LocalFileSystem for dev) but emits a
warning at startup. Set both for the production shape.

## Quick start: MinIO locally

```bash
# 1. Start MinIO in docker.
docker run -d --rm -p 9000:9000 \
    -e MINIO_ROOT_USER=minio \
    -e MINIO_ROOT_PASSWORD=minio12345 \
    --name agentdb-minio \
    minio/minio server /data

# 2. Create a bucket.
AWS_ACCESS_KEY_ID=minio AWS_SECRET_ACCESS_KEY=minio12345 \
    aws --endpoint-url=http://localhost:9000 s3 mb s3://agentdb

# 3. Run agentdb-server against MinIO.
AGENTDB_KV_BACKEND=slatedb \
AGENTDB_OBJECT_STORE=s3 \
AGENTDB_S3_BUCKET=agentdb \
AGENTDB_S3_ENDPOINT=http://localhost:9000 \
AWS_ACCESS_KEY_ID=minio AWS_SECRET_ACCESS_KEY=minio12345 \
    cargo run --release --bin agentdb-server
```

The `scripts/smoke-s3.sh` script runs the whole flow end-to-end —
boot MinIO, create bucket, launch server, append+fetch, wait for
cold-tier sweep, assert segments land in the bucket, tear it all
down. Use it as a reference.

## AWS production walkthrough

1. **Create the bucket** in your target region:

   ```bash
   aws s3 mb s3://agentdb-prod-us-east-1 --region us-east-1
   ```

2. **Create an IAM role or user** with this policy attached:

   ```json
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Action": [
         "s3:GetObject",
         "s3:PutObject",
         "s3:DeleteObject",
         "s3:ListBucket"
       ],
       "Resource": [
         "arn:aws:s3:::agentdb-prod-us-east-1",
         "arn:aws:s3:::agentdb-prod-us-east-1/*"
       ]
     }]
   }
   ```

3. **Launch the server**:

   ```bash
   AGENTDB_KV_BACKEND=slatedb \
   AGENTDB_OBJECT_STORE=s3 \
   AGENTDB_S3_BUCKET=agentdb-prod-us-east-1 \
   AGENTDB_S3_REGION=us-east-1 \
   AWS_ACCESS_KEY_ID=<KEY> AWS_SECRET_ACCESS_KEY=<SECRET> \
       ./agentdb-server
   ```

## Observed behavior

- **Startup** performs a `list` probe under the `agentdb/` prefix.
  Fails fast with a clear message on bad creds, wrong region, or
  unreachable endpoint.
- **Scan latency** measured by
  `crates/agentdb-core/benches/mvcc_bench.rs` on a 1000-event
  session:
  - RocksDB: **~196 µs**
  - SlateDB on LocalFileSystem: **~527 µs** (~2.7× RocksDB)
  - SlateDB on S3: not measured in CI; add ~30 ms per object-store
    round-trip as a rough production estimate.
- **Snapshot isolation** works identically on both backends. SlateDB
  uses its native `Db::snapshot()` primitive, which returns a
  point-in-time `Arc<DbSnapshot>` pinned to a sequence number (the
  "Tier 1 native" resolution of the snapshot spike —
  `docs/superpowers/notes/2026-04-19-m11-slatedb-spike.md`).
- **Cold-tier transitions** run every `AGENTDB_T_COLD_SECS` seconds
  (default 60). Segments land in the same bucket under
  `boxes/{box_id:04x}/cold/…`.

## Cost

S3 PUTs at scale are not free. For ~1k appends/sec, baseline is
~$4–8/day in S3 API calls before storage. SlateDB batch-commits
amortize some of this but don't eliminate it. `docs/agent-db.md` §3
argues the cold-tier storage economics ($0.004–0.023/GB/month vs
EBS at $0.08/GB/month) overwhelm the API-call cost for agent
workloads where 95% of data is cold.

## Known limitations

- **Drop pause on shutdown**: `SlateKvStore::Drop` blocks the caller
  thread waiting for SlateDB to flush its memtable to S3. Long
  flushes can visibly pause process exit. Committed writes are
  already durable on object storage, so abrupt termination only
  loses the last in-memory batch.
- **MinIO gotchas**: MinIO requires path-style addressing and HTTP.
  `AGENTDB_S3_ENDPOINT=http://localhost:9000` handles both via the
  `object_store` crate's `allow_http` +
  `virtual_hosted_style_request(false)` settings.
- **No data migration** from RocksDB to SlateDB. The two backends
  have incompatible on-disk formats and independent storage roots.
  There is no dual-read, no import tool, no shared schema.
- **Single-node**: SlateDB-on-shared-S3 technically enables
  multi-node topology, but AgentDB itself still assumes a single
  writer per box. Multi-node coordination (write fencing, leader
  election) is a future milestone.

## Troubleshooting

**"object store liveness probe failed" at startup**: the bucket
doesn't exist, the credentials are wrong, the region is
mismatched, or the endpoint is unreachable. The error names the
`AGENTDB_S3_*` env vars so you can diagnose. For MinIO, confirm
the container is up: `curl http://localhost:9000/minio/health/ready`.

**Append succeeds but no segments appear in the bucket**: the
cold-tier transition runs on a timer (`AGENTDB_T_COLD_SECS`,
default 60). Either wait for a session to go idle past the
threshold, or force a transition via `POST /api/admin/tier/force`.

**`cargo run` hangs on Drop when shutting down**: a large memtable
is flushing to S3. Expected on a loaded server; wait for it to
finish.

**`AGENTDB_KV_BACKEND=slatedb` but segments are going to local
disk**: you forgot to set `AGENTDB_OBJECT_STORE=s3`. The startup
warning tells you this — check the server logs for the nudge
message.
